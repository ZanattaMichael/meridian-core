# The configuration management resource types

The `ansible`, `puppet`, `openvox`, `chef`, `salt` and `cloud-init` targets share
six resource types. A resource written with them compiles for any of the six,
within what each tool can do. OpenVox reads the language Puppet reads, so wherever
this page says Puppet, the same holds for `openvox`.
Anything outside these tables is refused, never dropped: a param a target does
not take, a state it cannot express, an action it cannot perform.

The kind of value each param takes is checked in one place, the same way on all
six targets, before a plugin applies its own rules: text where a name is wanted
(`name`, `path`, `mode`, `shell`), true or false where a flag is wanted
(`enabled`, `system`, `append`), a whole number for `uid` and `gid`, a list for
`groups`, `members` and `ssh_authorized_keys`. A value of the wrong kind is
refused as `invalid-param` with the same message whichever target the document
names, so a document that compiles for Ansible does not fail on Chef for a
reason that has nothing to do with Chef. The strict reading was chosen on
purpose: a number or a list where a name is wanted, or `yes` where true is
wanted, is refused rather than passed to the tool to interpret
([decision 0024](../decisions/0024-shared-param-kinds-are-checked-once-strictly.md)).

How the rest of a configuration management document is written is in
[the configuration management flavour](dsl/configuration-management.md).

The [conformance matrix](conformance-matrix.md) is this page as a table of
facts: about ninety small documents, each compiled by all six targets, with how
every compile came out. It is generated by a test, so it is always what the
plugins do today.

Other targets do not use these types. Their resources are the tool's own; see
[documents, resources and targets](../concepts/ir-overview.md#two-families-of-types).

## `package`

| | |
|---|---|
| Params | `name` (required). Salt also takes `version`, with `present` only. cloud-init also takes `version`, to pin one |
| States | `present` (default), `absent`, `latest`. cloud-init: `present` only, because a first boot installs and cannot remove or track |
| Can be notified | no |

```yaml
- id: nginx_pkg
  type: package
  params:
    name: nginx
```

## `service`

| | |
|---|---|
| Params | `name` (required), `enabled` (true or false: start at boot) |
| States | `running` (default), `started` (the same), `stopped`. Ansible and cloud-init also take `restarted` and `reloaded` |
| Can be notified | Ansible, Chef, Salt and cloud-init: `restart`, `reload`, `start`, `stop`. Puppet: `restart` (or `refresh`) only |

Puppet, Chef and Salt describe a state a node is left in, and "restarted" is not
one, so they refuse it as a state. Salt also refuses `restart` and `reload`
aimed at a service whose state is `stopped`. To restart a service when something changes, use
`notifies`.

cloud-init has no module for services. A service compiles to `systemctl`
commands that run at the end of the first boot, with a warning that the image
must use systemd.

```yaml
- id: nginx_svc
  type: service
  state: running
  params:
    name: nginx
    enabled: true
```

## `file`

| | |
|---|---|
| Params | `path` (required), `content`, `owner`, `group`, `mode`. cloud-init also takes `encoding` and `append` |
| States | `present` (default) or `file`, `directory`, `absent` |
| Can be notified | no |

Write `mode` as a quoted string (`"0644"`), so it is not read as a number. A
directory has no `content`: every target refuses the two together. On Salt a `file` with no `content` creates the file
if it is missing, a directory is created with its parents, and the attributes of
an absent file are left out with a warning.

On cloud-init a file in state `present` must have `content`, because cloud-init
writes whole files, and the `directory` and `absent` states compile to commands
(`install -d`, `rm -rf`).

```yaml
- id: app_conf
  type: file
  params:
    path: /etc/app/app.conf
    content: "workers = 8\n"
    owner: root
    mode: "0640"
```

## `user`

| | |
|---|---|
| Params | `name` (required), `uid`, `home`, `shell`, `system`, `groups`. cloud-init also takes `gecos`, `primary_group`, `lock_passwd`, `sudo` and `ssh_authorized_keys` |
| States | `present` (default), `absent`. cloud-init: `present` only |
| Can be notified | no |

`groups` are supplementary groups. On Chef, whose `user` resource has a primary
group only, each one becomes a separate membership block that adds the user to
the group and leaves its other members alone. On Salt the list is complete: the
user is removed from any group not in it.

## `group`

| | |
|---|---|
| Params | `name` (required), `gid`, `system`. cloud-init takes `name` and `members` only: it cannot choose a group's id |
| States | `present` (default), `absent`. cloud-init: `present` only |
| Can be notified | no |

## `exec`

The escape hatch: run a command. It has no state, because there is nothing to
converge on.

| | |
|---|---|
| Params | `command` (required), `chdir`, `creates` (skip when this path exists), `shell` (true to run through a shell). Ansible, Salt and cloud-init also take `removes` (run only when this path exists) |
| States | none |
| Can be notified | `run` |

An `exec` runs on every apply unless `creates` says it is already done, so a
plan for a document with a bare `exec` always shows a change. A notified `exec`
runs in its place in the order, and once more when it is notified. On
cloud-init every `exec` runs once, on the first boot, and stops the commands
after it if it fails.

Salt always runs a command through a shell. So that a document means the same
on every target, Salt refuses a command that holds shell syntax unless the
resource says `shell: true`; see [the Salt page](../targets/salt.md#exec).

```yaml
- id: warm_cache
  type: exec
  params:
    command: /usr/local/bin/warm-cache --all
    chdir: /srv/app
    creates: /var/cache/app/warm
```

## References

On these targets a resource has nothing to read during the apply: all it has is
what the document says. So `${id.param}` inside a param is settled when the
document is compiled. It becomes the value the document gives that param on the
resource `id`.

```yaml
- id: site_root
  type: file
  state: directory
  params:
    path: /srv/app

- id: index
  type: file
  params:
    path: ${site_root.path}/index.html   # /srv/app/index.html
    content: hello
```

A reference that is the whole value of a param keeps the type of what it reads,
so `groups: ${app_user.groups}` is a list. Inside longer text it must read a
single value. A reference does not order the two resources; use `dependsOn` for
that.

A reference that cannot be settled is refused with the rule `invalid-reference`:
a resource the document does not declare, a param that resource does not set, a
bare `${id}`, or anything that is not `${id.param}`. Write `$${` for a literal
`${`, as a shell script in a file's `content` may need. `runtimeWhen` is not
touched: it is the tool's own language.

## What every resource can carry

| Field | Meaning | Where |
|---|---|---|
| `dependsOn` | order | every target ([how](../concepts/dependencies.md)) |
| `notifies` | react to a change | where the tool can ([matrix](capability-matrix.md)) |
| `runtimeWhen` | a condition checked on the node during the apply, written in the tool's own language | Ansible (a `when:` expression), Chef (the Ruby of an `only_if` guard), Salt (a Jinja expression over grains and pillar). Puppet refuses it: a catalog is compiled before it reaches the node. cloud-init refuses it: it evaluates nothing per resource |
